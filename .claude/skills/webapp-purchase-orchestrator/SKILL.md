# 교복구매 길라잡이 웹앱 오케스트레이터

## 실행 모드

**서브 에이전트 파이프라인**(팀 통신 불필요 — 각 단계 산출물이 파일로 다음 단계 입력이 되는 순차 의존 작업). `Agent` 도구로 각 에이전트를 순서대로 호출하며, 모든 호출에 `model: "opus"`를 명시함.

## 팀 구성

| 에이전트 | 역할 | 호출 시점 |
|---|---|---|
| `web-ux-designer` | 화면 와이어프레임·디자인 시스템·접근성 기준 설계 | WP-01(완료됨, 재작업 시에만) |
| `web-frontend-engineer` | 마스터 데이터 JSON 구조화(WP-02) + Static-first 웹앱 구현(WP-03) | WP-02, WP-03 |
| `quality-compliance-reviewer` | 접근성·서버 미경유·HWPX 토큰 일치·원본 보존 경계 검토 | 각 단계 완료 전 |

## Source of Truth (반드시 먼저 확인)

`0-1.교복계약 웹앱개발-프롬프트.txt`(구현 원칙)·`개발문서/0-2.교복 학교주관구매 웹앱 — 화면 구성 및 디자인 계획.md`(IA·데이터모델·화면설계)·`첫화면\교복 학교주관구매 웹앱 화면 디자인.pdf`(화면 6종 시안)가 이 프로젝트의 최상위 근거임(2026-09-25 사용자 제공). 업무절차·서식 원문은 교복 매뉴얼 HWPX를, 데이터 구조는 Excel 자동화 파일을 따른다는 이원 원칙(`0-1.txt` §1)을 항상 유지함.

## Phase 0: 컨텍스트 확인 (매 실행 시 먼저 수행)

1. `개발문서/웹앱_계획.md`를 읽어 WP-01/02/03의 현재 상태를 확인함.
2. `_workspace/05_web/`(또는 `/data`) 하위에 마스터 데이터 JSON 4종(`contract-methods.json`/`workflows.json`/`forms.json`/`fields.json`) 존재 여부로 재개/신규를 판별함:
   - 없음 → **WP-02부터 착수**
   - 있고 사용자가 부분 수정 요청 → **해당 마스터만 재작성**
   - 있고 WP-03 산출물(웹앱 소스)도 있음 → **WP-03 이어서 진행**
3. `ADR-002`가 여전히 최신 상태인지 확인함 — 사용자가 이 세션에서 아키텍처 결정(서버 유무, HWPX 생성 위치, 첫 화면 IA)을 다시 바꿨다면 `ADR-002`·`개발문서/웹앱_prd.md`·`개발문서/웹앱_계획.md`·`개발문서/웹앱_trd.md`를 먼저 갱신한 뒤 진행함.

## 실행 절차

1. **WP-01(설계)**: 이미 DONE(사용자 제공 스펙 기준). 사용자가 화면설계 변경을 요청하면 `web-ux-designer`를 호출해 `_workspace/05_web/웹앱_UX설계.md`를 갱신함 — 이때 `web-ux-designer`는 `frontend-design` 스킬을 호출하고 `ui-ux-pro-max-skill`(설치된 스킬 아님, 참고 저장소) 방법론을 활용함(`개발문서/웹앱_계획.md` §4).
2. **WP-02(마스터 데이터 구조화) 착수**: `web-frontend-engineer`를 호출해 `개발문서/웹앱_task.md`의 WP-02-01~05(계약방법/Workflow/Form/Field Master + Template Mapping)를 순서대로 작성하게 함. **이 5개가 모두 완료되기 전에는 WP-03 UI 코드를 작성하지 않음**(`0-1.txt` §22, `개발문서/웹앱_체크리스트.md` WP-02 게이트). 완료 후 `quality-compliance-reviewer`가 Excel 원본(`frmContractGuide`, `개발문서/서식_매핑표.md`, `개발문서/입력데이터_사전.md`)과의 1:1 일치 여부를 검토함.
3. **WP-02 완료 후 정지**: 산출물을 사용자에게 요약 보고하고, **사용자 확인 없이 WP-03으로 자동 진행하지 않음**(사용자 요청 "천천히 진행" 반영).
4. **WP-03(구현) 착수**: `web-frontend-engineer`를 호출해 `개발문서/웹앱_task.md`의 WP-03-01~13을 구현하게 함. HWPX는 `scripts/hwpx_token_fill.ps1`·`hwpx_school_footer_fill.ps1` 로직을 클라이언트 사이드로 포팅해 실제로 생성함(안내 문구로 대체하지 않음). 완료 후 `quality-compliance-reviewer`가 `개발문서/웹앱_test.md` 전 항목을 검토함.
5. 각 단위 완료 후에만 `개발문서/웹앱_계획.md`·`개발문서/웹앱_task.md`·`개발문서/웹앱_체크리스트.md`·`개발문서/웹앱_로그.md`를 갱신함. Critical/High 결함이 남으면 `DONE`으로 표시하지 않음.

## 데이터 전달 규칙

- 중간 산출물: `/data/*.json`(마스터 데이터), `_workspace/05_web/웹앱_구현기록.md`.
- 최종 산출물: 웹앱 프로젝트 소스(배포 경로는 WP-03에서 사용자와 확정: 학교 PC 로컬 / GitHub Pages / Vercel).
- 기초자료 필드값(학교명·담당자 성명 등 실제 값)은 Git·로그·대화에 원문으로 기록하지 않음 — 필드 ID·타입만 다룸.

## 오류 및 중단 처리

- 마스터 데이터가 미완성인 채로 WP-03 요청이 들어오면, 코드를 작성하지 않고 WP-02부터 진행하도록 사용자에게 안내함(`0-1.txt` §22 원칙 강제).
- `web-frontend-engineer`가 서버·DB가 필요한 기능을 요구하면 구현하지 않고 범위 초과로 보고함 — `ADR-002` 재검토는 사용자 결정 사항임.
- `quality-compliance-reviewer`가 Critical(서버 전송 발견, HWPX 토큰 불일치, 매뉴얼에 없는 절차 임의 추가)을 발견하면 즉시 반려함.

## 테스트 시나리오

- 정상 흐름: WP-02 마스터 데이터 5종 완료 → `quality-compliance-reviewer` 검토 통과 → 사용자 확인 → WP-03 구현 → `개발문서/웹앱_test.md` 전 항목 PASS → WP-03 `DONE`.
- 에러 흐름: WP-02 완료 전 사용자가 "빨리 화면부터 만들어줘"라고 요청해도, 마스터 데이터 없이 UI를 만들면 서식-단계 연결이 틀릴 위험이 크므로 이 원칙(`0-1.txt` §22)을 설명하고 WP-02 우선 진행을 제안함(단, 사용자가 명시적으로 원칙을 무시하라고 재지시하면 그 지시를 따르되 위험을 기록함).
