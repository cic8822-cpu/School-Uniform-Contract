# 3. 현재까지 확인된 중요한 사실

기존 `용역계약갈라잡이.xlsm`에는 다음과 같은 구조가 존재하므로 반드시 벤치마킹한다.

- 메인 화면
- 기본정보 입력하기
- 계약서식
- DB / Ref_data
- 학교정보
- 각종 참조 테이블
- Print_sheet
- 기본정보 1회 입력 후 여러 서식 자동반영
- 출력할 서식 선택
- 선택한 서식의 인쇄 범위 조합
- 학교정보 검색 및 자동입력 개념
- 계약 관련 정보와 서식을 하나의 파일에서 처리하는 구조

새 교복 길라잡이는 이 구조를 그대로 복제하는 것이 아니라 좋은 구조와 UX를 추출하여 교복업무에 맞게 재설계한다.

교복 매뉴얼에는 여러 단계의 업무 절차와 다수의 공문·계약·평가·가정통신문·설문·검수 관련 서식이 포함될 가능성이 있다.

자동 추출 결과만으로 서식 개수를 확정하지 않는다.

먼저 HWPX의 텍스트, 표, 이미지, 섹션, 문단, 첨부 서식 구조를 분석하여 실제 서식 인벤토리를 확정한다.

# 4. PM-Agent의 기본 행동 원칙

다음 원칙은 프로젝트 전체에 적용한다.

1. 질문만 하고 작업을 멈추지 않는다.
2. 사용자가 답하지 않은 사소한 사항은 합리적인 가정을 세우고 `가정/결정사항`에 기록한 뒤 계속 진행한다.
3. 프로젝트 진행을 막는 치명적인 불확실성만 사용자에게 질문한다.
4. 가능한 작업은 직접 수행하고 결과 파일을 만든다.
5. “다음에 하면 됩니다”라는 조언으로 끝내지 않는다.
6. 각 단계 완료 후 산출물을 검증하고 문제가 있으면 스스로 수정한다.
7. 하나의 문제 때문에 전체 프로젝트를 중단하지 않는다.
8. 새로운 요구사항이 나오면 기존 PRD와 계획에 반영하고 변경 이력을 남긴다.
9. 정책·법령·교육청 지침과 관련된 정보는 추측하지 않는다.
10. 외부 리서치 결과는 출처와 확인일을 기록한다.
11. `사전리서치.md`에서 `[AI]`, `미확인`, `추정` 등으로 표시된 내용은 검증된 사실과 구분한다.
12. 라이브러리 또는 skill의 API·명령어·파일구조를 추측해서 사용하지 않는다.
13. 외부 도구를 사용하기 전에 설치된 skill, README, 예제, 실제 소스코드를 확인한다.
14. 숨겨진 내부 추론을 출력하지 말고 사용자에게는 판단 근거·결정·위험·다음 행동만 간결하게 보여준다.

# 5. grill-me 요구사항 확정 단계

프로젝트 초반에는 `grill-me` skill이 존재하면 이를 사용한다.

skill이 없다면 동일한 목적의 인터뷰를 직접 수행한다.

단, 질문을 한 번에 수십 개 나열하지 않는다.

가장 중요한 질문부터 최대 3~5개씩 질문하고 다음 네 범주를 확정한다.

- 반드시 포함할 서식
- 1차 MVP와 후속 서식 구분

### B. 자동입력 데이터
예:
- 학교명
- 학교 주소
- 학교 전화번호
- 담당자
- 교장
- 학년도
- 관련 공문번호
- 예정 인원
- 동복 단가
- 하복 단가
- 상한가격
- 계약방법
- 납품일
- 평가위원
- 업체정보
- 계약금액
- 기타 반복 입력값

### C. 출력
- Excel 인쇄
- PDF
- HWPX
- 개별 서식 출력
- 여러 서식 일괄 출력

### D. 실제 배포환경
- Excel 버전
- Windows 환경
- 한컴오피스 설치 여부
- VBA 사용 허용 여부
- Python 또는 별도 실행환경 허용 여부
- 학교 보안정책
- 웹사이트 접근 제한 여부

이미 자료에서 확인 가능한 질문은 사용자에게 다시 묻지 않는다.

# 8. Excel MVP 설계 원칙

Excel은 다음 정보구조를 기본안으로 설계한다.

### 01_교복구매_워크플로우

첫 화면이며 교복구매 전체 단계를 시각적인 Workflow로 제공한다.

각 단계는 클릭 가능한 버튼 또는 링크로 만든다.

클릭하면 다음 중 적절한 위치로 이동한다.

- 해당 단계 설명
- 체크리스트
- 관련 서식 목록
- 관련 서식 작성 화면

### 02_기초자료_입력

반복 사용되는 정보를 한 번만 입력한다.

사용자가 직접 입력하는 셀과 자동계산 셀을 시각적으로 명확히 구분한다.

가능하면 다음을 활용한다.

- 드롭다운
- 날짜 데이터 검증
- 학교정보 검색
- 필수값 검증
- 오류 메시지

### 03_서식선택_출력

전체 서식을 업무단계별로 보여준다.

다음 기능을 검토한다.

- 전체선택
- 단계별 선택
- 자주 쓰는 서식 선택
- 개별 미리보기
- Excel 출력
- 선택 서식 일괄 인쇄
- PDF 생성
- HWPX 생성 요청

### 시스템/참조 시트

- DB
- Ref_data
- 학교정보

- 정렬
- 결재영역
- 수신/경유/제목
- 붙임
- 시행/접수

- 가정통신문 구성

- 인쇄 페이지

HWPX 원본과 Excel은 렌더링 엔진이 다르므로 “픽셀 단위 완전 동일”을 무조건 목표로 하지 않는다.

재현도를 다음과 같이 평가한다.

- A: 실무 출력 가능
- B: 내용은 정확하나 레이아웃 추가 조정 필요
- C: Excel 재현에 부적합하며 HWPX 원본 자동화 방식 사용 권장

단, kordoc의 API나 기능을 기억 또는 추측으로 사용해서는 안 된다.

실제 작업 시작 전에 반드시 다음 순서로 확인한다.

1. 현재 환경에서 `kordoc` 또는 관련 skill의 존재 여부 확인
2. README 및 사용법 확인
3. example/example code 확인
4. package 구조 확인
5. HWPX 읽기/쓰기/치환 관련 실제 지원 기능 확인
6. 샘플 HWPX 사본으로 최소 기능 테스트
7. 성공한 API 사용방식을 프로젝트 문서에 기록

결과는 `kordoc_기술검증.md`에 기록한다.

최소 검증항목:

- 기존 HWPX 열기
- 문서 구조 탐색
- 텍스트 추출
- 표 구조 접근
- 텍스트 치환
- 표 안의 값 치환
- 원본 스타일 보존
- 새 HWPX 저장
- 저장된 HWPX 재오픈 가능 여부
- 한컴오피스에서 정상 열림 여부
- 원본과 레이아웃 차이
- 대량 서식 처리 가능성

HWPX 자동화 기본전략은 가능하다면:

`원본 HWPX 템플릿 유지 → 지정 변수만 치환 → 새 HWPX 저장`

방식을 우선한다.

이는 HWPX 레이아웃을 새로 재구성하는 방식보다 원본 보존성이 높은지 우선 검토한다.

예:

`{{SCHOOL_NAME}}`
`{{SCHOOL_ADDRESS}}`
`{{SCHOOL_YEAR}}`
`{{CONTRACT_AMOUNT}}`
`{{DELIVERY_DATE}}`

단, 실제 원본 문서를 임의로 훼손하지 않는다.

원본 HWPX의 필드 또는 텍스트를 어떻게 변수화할지는 먼저 복사본에서 검증한다.

kordoc이 특정 기능을 지원하지 않는 경우에만 다음 대안을 순차 검토한다.

1. HWPX ZIP/XML 직접 조작
2. 한컴오피스 자동화 API
3. 별도 HWPX 템플릿 엔진
4. PDF를 1차 출력형식으로 제공

kordoc으로 해결 가능한 작업에 대해 별도의 복잡한 구현을 먼저 만들지 않는다.

핵심 사용자는 학교의 교사 및 행정실 직원이며 매일 사용하는 시스템이 아닐 수 있다.

1. 지금 어느 단계인지 알 수 있다.

3. 필요한 서식을 바로 찾을 수 있다.
4. 어떤 정보를 입력해야 하는지 알 수 있다.
5. 기존에 입력한 정보는 반복 입력하지 않는다.
6. 작성 전 누락사항을 알려준다.
7. 결과물을 쉽게 출력할 수 있다.

# 23. /goal 실행 방식

초기 분석 및 핵심 질문이 끝나고 `prd.md`와 `계획.md`의 첫 버전이 만들어지면 프로젝트 목표를 `/goal`로 등록하여 실행한다.

1차 `/goal` 완료 후 2차 `/goal`:

“검증된 교복구매 길라잡이 Excel/HWPX 데이터 모델과 업무 Workflow를 기반으로 학교 담당자가 별도 교육 없이 사용할 수 있는 교복구매 웹앱을 구축한다. UX/UI 설계와 개선에는 ui-ux-pro-max-skill을 활용하며, HWPX 문서생성에는 kordoc 기반 구조를 우선 재사용한다.”

/goal 수행 중에는 항상 `계획.md`에서 아직 DONE이 아닌 가장 높은 우선순위 작업을 선택한다.

실행 루프:

1. 현재 상태와 다음 작업 확인

4. 산출물 생성
5. 자동/수동 검증
6. 오류 수정
7. `계획.md` 상태 업데이트
8. `결정사항.md` 또는 `CHANGELOG.md` 업데이트
9. 다음 미완료 작업 진행

작업이 막히면 BLOCKED 사유를 기록하고 독립적인 다음 작업을 계속한다.
