## HIGH

### H-1. 계산 필드 19개 Form에서 사용자 입력 필드와 중복되어 있음

`K-01`~`K-04`는 Field Master에서 명시적으로 `required: "computed"`이고 산식/비식별 집계 규칙을 가진다 (`fields.json:1307-1403`, `입력데이터_사전.md:56-59`). 하지만 Form Master 19개에서 이 IDs가 `inputFieldIds`와 `computedFieldIds` 양쪽에 동시에 들어 있다. 예를 들어 F-021은 `K-01`, `K-02`를 입력 배열에 넣은 뒤(`forms.json:1433-1446`) 계산 배열에도 다시 둔다(`forms.json:1456-1459`). 반대로 F-008은 K-01을 계산 배열에만 넣어 동일 스키마 내에서도 일관되지 않다 (`forms.json:540-556`).

영향 Form: F-004, F-005, F-006, F-009, F-011, F-014, F-015, F-016, F-018, F-021, F-024, F-031, F-035, F-036, F-039, F-041, F-043, F-051, F-052.

이대로 구현하면 기초자료 UI/누락값 판정이 계산금액·평가총점·만족도 평균을 직접 입력하게 하거나, 재계산 전 누락값으로 오인할 수 있다. 이는 PRD의 Single Source of Truth와 계산 검증 요구를 위반한다 (`웹앱_prd.md:43,45`).

**수정 요구**: `inputFieldIds`를 실제 사용자 입력 Field만 남기고, 모든 참조 Field가 필요하면 별도 `referencedFieldIds`를 도입한다. `computedFieldIds`는 입력 배열과 항상 서로소라는 검증을 추가하고, F-041의 계산 필수값도 “사용자 입력 필요”가 아니라 선행값 충족 후 계산 대상으로 처리한다.

### H-2. Workflow Master에 WFR-03의 체크리스트·주의사항·매뉴얼 조항 인용 데이터가 없음

WFR-03은 각 단계에 “해야 할 일 체크리스트”, “주의사항”, 그리고 “매뉴얼 조항 번호까지 인용”을 요구한다 (`웹앱_prd.md:41`). 그러나 Workflow step은 `stepNo`, 이름, 설명, `assignee`, Form ID/라벨만 제공하며 (`workflows.json:16-73`, `146-343`), `assignee`조차 업무설명 주어에서 도출한 값이라 “매뉴얼 확인 필요”로 적혀 있다 (`workflows.json:27,87,157` 등). 단계별 `checklistItems`, `cautions`, `manualReferences` 또는 원문 위치가 없다.

UI 구현자는 이 필수 정보를 임의 작성하거나 표시하지 못하게 된다. 둘 다 P0 수용 기준 실패다.

**수정 요구**: 각 20개 Step에 원문 기반 `checklistItems[]`와 `cautions[]`를 추가하고, 각 항목에 매뉴얼 번호·쪽·조항/문단 위치를 연결한다. 근거가 없는 담당구분은 확정값으로 표시하지 않도록 상태/표시 정책도 포함해야 한다.

### H-3. 계약방법별 서식 필터를 위한 데이터가 19개 Form에서 미확정임

PRD는 52개 전체 서식의 계약방법 필터를 요구하고 (`웹앱_prd.md:42`), WP-02 계획도 Form Master에 “사용 계약방법”을 넣도록 명시한다 (`웹앱_계획.md:37`). 하지만 F-001~F-007, F-013, F-026, F-028, F-044~F-052 총 19개는 `contractMethods: []`와 “계약방법별 사용 여부 매뉴얼 확인 필요”만 가진다. 예시는 F-001 (`forms.json:57-58`), F-013 (`916-917`), F-026 (`1757-1758`), F-044 (`3014-3015`)이다.

빈 배열을 “모든 계약방법” 또는 “어느 계약방법에도 해당하지 않음”으로 해석하면 모두 오답이다. 현재 Master만으로 WFR-04 필터 결과를 구현할 수 없다.

**수정 요구**: 매뉴얼 근거로 19개 각각의 적용 계약방법을 확정한다. 확정 전에는 `unknown` 상태를 빈 배열과 구별하고 해당 필터에서 “확인 필요”로만 노출하도록 UI 계약을 명시해야 한다. WP-02 완료 판정은 근거 확보 전에는 불가하다.

### H-4. 일반경쟁입찰(CM-04)의 11단계가 2단계 입찰 Workflow를 그대로 재사용하지만, 별도 절차 근거가 없음

CM-04는 `WF-BID`에 연결돼 있고 33개 Form을 동일하게 사용한다 (`contract-methods.json:141-188`). 그러나 데이터 자체가 “일반경쟁입찰 전용 절차는 Excel에 별도 정의가 없어 매뉴얼 확인 필요”라고 인정한다 (`contract-methods.json:12`). 실제 VBA의 `입찰계약` 1단계 설명은 “2단계 입찰(규격·가격 동시)이 원칙”이라고 되어 있다 (`build_excel_v1_vba.ps1:2965-2968`).

PRD는 2단계계약과 일반입찰계약 각각에 정확한 11단계를 보여야 한다 (`웹앱_prd.md:40`). 현재 데이터는 2단계 입찰 절차를 일반경쟁입찰 사용자에게 사실처럼 제시할 수 있어 계약 업무상 위험이 크다.

**수정 요구**: 매뉴얼 원문으로 일반경쟁입찰의 절차·Form 적용을 확인해 별도 Workflow 또는 근거가 붙은 공유 Workflow를 만든다. 근거 확보 전에는 CM-04에서 확정 절차로 진행시키지 말고 “매뉴얼 확인 필요” 상태로 제한해야 한다.

### H-5. `outputMethod: both`가 HWPX에 실제 반영되는 Field 범위를 보장하지 않아 완성 문서로 오인될 수 있음

Template Mapping은 실제 HWPX 토큰이 6종뿐이고(`template-mapping.md:22-35`), F-021처럼 13개 Field를 쓰는 Form도 HWPX 토큰은 학교명·학년도 2개뿐이다 (`forms.json:1433-1459,1473-1477`). 그럼에도 47개 Form이 `outputMethod: "both"`로 표시된다. 이 값만으로는 HWPX가 해당 Form의 필수/계산/반복 Field를 모두 반영하는지, 공통 토큰만 반영하는지 구분할 수 없다.

WFR-05·WFR-08·WFR-09는 입력값 자동반영과 실제 HWPX 작성을 요구한다 (`웹앱_prd.md:43,46-47`). 현재 메타데이터로 “작성가능”이나 HWPX 버튼을 제어하면 필수값이 비어 있는 원본 양식을 완성 문서로 오인시킬 수 있다.

**수정 요구**: Form별 `hwpxSupportedFieldIds`/`hwpxCoverage`와 완료 기준을 추가한다. 전체 자동반영이 아니라면 HWPX 출력 상태를 “공통 토큰만 반영”으로 명시하고, P0의 완성문서 출력 범위와 불일치를 WP-03 착수 전에 결정해야 한다.
