## 2. 문제 인식

기존 웹앱 설계에는 다음과 같은 과제가 있음:

1. **개발 난이도 높음**: 백엔드 서버, 데이터베이스, 인증/권한, API 설계, 배포/운영 전부 미시작
2. **서버 운영 부담**: SSL, 도메인, 업데이트, 장애 대응 등 지속적 관리 필요
3. **개인정보 경계 복잡**: 입력값을 서버에 저장하면 전송·저장·삭제 전담 ADR 필수
4. **P2-03 ADR 대기**: 웹앱 HWPX 이관 전제 조건인 "Excel 연계 곤란" 판정이 아직 없음
5. **중복 작업 위험**: 엑셀에서 이미 구현한 출력 로직(VBA 매크로)을 웹에서 재구현해야 함

## 3. 제안: 스트레이트(Strapi) + 엑셀 파일 방식

### 핵심 아이디어
- **스트레이트(Strapi)**: 헤드리스 CMS로, 학교의 **공통 기초자료(학교명·학년도·담당자 등 2~3개 필드)만** 저장
- **엑셀(XLSM)**: 기존과 동일하게 `기초자료입력` 시트 + 서식 시트 + VBA 매크로를 유지
- **웹 프론트엔드**: 정적 사이트로, 절차 안내·서식 목록·출력 버튼만 렌더링
- **HWPX 생성**: `hwpx_token_fill.ps1`이라는 **공통 인터페이스**로, 엑셀이든 웹이든 독립적으로 호출 가능

### 작동 흐름
```
사용자(학교 담당자)
  ├── 웹에서 "기초자료 입력" 팝업 → 데이터를 스트레이트에 저장
  └── 또는 기존 엑셀 파일을 직접 사용 (로컬)
       ↓
"출력" 클릭
  ├── 웹 경로: 백엔드가 hwpx_token_fill.ps1 호출 → HWPX 생성 → 다운로드
  └── 엑셀 경로: VBA 매크로가 hwpx_token_fill.ps1을 Shell로 호출 → HWPX 생성 → 저장
```

### HWPX 토큰 치환 인터페이스 (공통)
```bash
hwpx_token_fill.ps1 -TemplatePath <hwpx> -JsonPath <학교데이터.json> -OutputPath <출력 hwpx>
```
이 명령어는 **누가 호출하느냐에 관계없이 동일**하게 작동합니다:
- 엑셀 VBA `Shell` 명령에서 호출
- 웹 백엔드(Node.js)에서 호출
- 데스크탑 PowerShell에서 수동 호출

## 4. 장단점 비교

### 스트레이트 + 엑셀 방식 (제안) vs 원래 계획(PRD FR-08)

| 평가 항목 | 제안 방식 (스트레이트 + 엑셀) | 원래 계획 (PRD FR-08) |
|---|---|---|
| **서버 운영** | 불필요 (정적 사이트 호스팅) | 필요 (백엔드 서버 + DB) |
| **데이터 저장** | 스트레이트에 학교명 2~3필드만 저장 | 모든 입력값을 서버에 영속 저장 |
| **개인정보 보안** | 엑셀 파일 자체가 학교 현장에 있으므로 서버 미경유 | 전송·저장·삭제 ADR 필수 |
| **개발 난이도** | 낮음 (정적 프론트 + 가벼운 백엔드) | 높음 (전체 백엔드 설계·구현) |
| **HWPX 출력** | `hwpx_token_fill.ps1` 공통 인터페이스로 동일 | 동일한 백엔드에서 생성 |
| **배포** | Vercel/Netlify 무료 정적 호스팅 | 자체 서버 호스팅 필요 |
| **모바일 대응** | ✅ 반응형 웹 | ✅ 웹 기본 |
| **엑셀 매크로 재사용** | ✅ VBA가 이미 출력 로직 보유 | ❌ 웹에서 재구현 필요 |
| **엑셀 독립 사용** | ✅ 파일만 있으면 웹 없이도 작동 | ❌ 웹 의존 |

## 5. 제안 사항

### 5.1 엑셀과 웹앱은 별개로 운영
- 두 플랫폼은 **독립적으로 배포**하며, 서로에게 의존하지 않음
- 엑셀은 학교 내부 로컬에서 사용 (Microsoft 365 기반)
- 웹은 누구나 접근 가능한 정적 사이트

### 5.2 HWPX 자동화는 공통 인터페이스로 연결
- `hwpx_token_fill.ps1`이 두 플랫폼 모두에서 호출 가능한 **유일한 HWPX 생성 엔진**
- 엑셀은 VBA에서 `Shell`로 이 스크립트를 호출
- 웹은 백엔드에서 이 스크립트를 호출
- 핵심은 **HWPX 템플릿 + JSON 데이터**라는 인터페이스가 동일하다는 점

### 5.3 웹은 절차 안내 + 서식 선택에 집중
- 웹의 주요 역할은 **교복구매 9단계 워크플로우 안내** + **서식 목록 제시** + **출력 버튼**
- 기초자료 입력은 팝업(수기 입력) 또는 엑셀 파일 업로드로 처리
- 실제 출력(엑셀·HWPX·PDF)은 엑셀 매크로나 백엔드 스크립트가 담당

### 5.4 서버 운영은 하지 않음
- 정적 사이트 호스팅(Vercel/Netlify/Cloudflare Pages 무료)만 사용
- 백엔드 서버 운영, DB 관리, SSL 인증서 갱신 등 불필요
- 스트레이트 헤드리스 CMS는 가벼운 콘텐츠 관리용 (학교명·학년도 정도)

### 5.5 교내 배포 전략
- 엑셀 파일: GitHub 릴리즈 또는 Google Drive 공유
- 웹: 정적 사이트 URL만 공유 (school-name.hwp-x.app 등)
- 각 학교가 엑셀 파일 + 웹 URL만 가지고 있으면 됨

## 6. 사용 편의성·배포 용이성 평가

### 사용자 경험(UX) 비교

**엑셀만 사용하는 경우:**
- ✅ 이미 구현 완료 (43종 Form ID, VBA 매크로 정상 작동)
- ✅ 학교 내부망이나 USB로 배포 가능
- ✅ 추가 설치 불필요 (Microsoft 365 이미 보유)
- ❌ 모바일에서 사용 어려움
- ❌ 9단계 안내가 시트 탐색으로 직관적이지 않음

**웹앱 + 엑셀 병행 시나리오:**
- ✅ 웹에서 절차를 먼저 안내받고, 필요한 서식 선택
- ✅ 웹에서 기초자료 팝업 입력 또는 엑셀 업로드
- ✅ 출력 버튼 클릭 → HWPX 자동 생성 다운로드
- ✅ 모바일·태블릿에서도 가능
- ✅ 정적 사이트이므로 서버 다운 걱정 없음
- ✅ 엑셀은 여전히 별도로 사용 가능 (로컬)

### 배포 용이성
- **엑셀**: `교복구매_길라잡이_YYYYMMDD_vN.xlsm` 파일 하나 배포
- **웹**: Vercel 프로젝트 배포 (GitHub 연동, 자동 배포)
- **스트레이트**: 헤드리스 CMS 콘텐츠만 관리 (학교명·학년도 목록)
- **총 배포 비용**: 거의 0원 (정적 호스팅 무료)

## 7. 결론

1. **엑셀과 웹앱은 별개 운영**이 맞음 — 두 플랫폼 모두 독립적으로 사용 가능
2. **HWPX 자동화는 공통 인터페이스(`hwpx_token_fill.ps1`)**로 연결하면 엑셀이든 웹이든 상관없이 작동
3. **스트레이트 + 정적 웹 + 엑셀** 조합이 사용자 편의성·시각적 우수성·배포 용이성 모두에서 우수
4. **서버 운영이 필요 없음** — 정적 호스팅만으로 충분
5. 엑셀의 VBA 매크로를 재사용하므로 **웹에서 출력 로직을 재구현할 필요 없음**

### 다음 단계 제안
- `hwpx_token_fill.ps1`을 웹 백엔드(Node.js 또는 PowerShell 호출)에서 실행할 수 있도록 래퍼 작성
- 스트레이트에 학교 기초자료(학교명·학년도)를 입력하는 CMS 콘텐츠 생성
- 웹 프론트엔드에 9단계 워크플로우 + 서식 목록 + 출력 버튼 구현
- 엑셀은 기존 배포본을 유지하되, 웹에서 업로드한 엑셀을 읽어 기초자료를 자동 채우는 기능 추가 여부 검토
