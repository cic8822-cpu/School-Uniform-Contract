### 5.2 근본 원인(확정)

kordoc CLI `fill -j <path>`는 JSON 파일을 읽을 때 UTF-8 BOM(`EF BB BF`)을 제거하지 않고 그대로 `JSON.parse()`에 전달하는 것으로 보임. BOM이 붙은 JSON은 파싱 단계에서 예외가 발생하고, CLI는 이를 구체적 원인 없이 `오류: 문서 처리 중 오류가 발생했습니다`로 뭉뚱그려 출력함(exit code 1). 문서 구조·필드 개수·JSON 크기와 무관하게 100% 재현되며, "두 개의 인식 필드만 담은 최소 JSON에서도 동일하게 실패"했다는 기존 기록과 정확히 일치함.

Windows 환경에서 PowerShell `Set-Content -Encoding UTF8`(Windows PowerShell 5.1 계열은 BOM 포함이 기본값)이나 구버전 메모장의 "UTF-8" 옵션 등은 기본적으로 BOM을 추가하므로, 이전 세션이 마스킹 JSON을 이런 도구로 저장했다면 내용·크기와 무관하게 항상 실패했을 것이라는 설명이 성립함. **실무 대응**: `-j`로 넘기는 JSON 파일은 반드시 BOM 없는 UTF-8로 저장함(예: bash heredoc, Python `문자열.encode('utf-8')`(BOM 미포함), PowerShell `[System.Text.UTF8Encoding]::new($false)`로 명시).

### 7.1 "가장 어려운 문제" — kordoc generate가 표 셀 안 이미지를 조용히 누락시킴

F-013의 대표 구조(섬유혼용률 rowspan 표 + 디자인 이미지가 든 표)를 축소 재현(`f013_slice.md`)해 `kordoc generate --preset 보고서`로 생성했더니:

- **`render`가 "이미지 0"을 보고**했고, 생성된 HWPX를 다시 Markdown으로 파싱(재파싱 왕복)하면 `![image](경로)` 자리에 **문자 그대로 `image`라는 텍스트**만 남아 있음을 확인함. 즉 이미지가 통째로 유실되는데도 `generate`·`validate` 어느 단계에서도 경고나 오류를 내지 않음 — **가장 위험한 종류의 조용한 실패**(silent failure)임.
- 표 안이 아니라 일반 문단에 이미지를 넣어도 동일하게 유실됨(`image_para_test.md`로 별도 확인) — 표 구조 문제가 아니라 **`generate` 명령 자체가 기본값으로는 마크다운 이미지 참조를 전혀 임베드하지 않는다는 사실**을 확인함.

### 7.2 근본 원인과 해법 확정

`kordoc generate --help`를 재확인해 원인을 특정함: `--image-dir <dir>` 옵션이 별도로 있고 "마크다운 이미지 참조(`![](x.png)`)를 이 디렉토리에서 읽어 실데이터 임베드"라고 명시되어 있음. **이 옵션을 지정하지 않으면 이미지 참조는 무시되고 `generate`·`validate`는 정상 종료해 실패를 숨김.**

수정된 방식(`f013_slice_img.md` + `--image-dir _workspace/02_hwpx/P2-01/repro/images`)으로 재실행한 결과:
- `[kordoc] 이미지 임베드: 2개` 로그로 임베드 확인 → `validate` 통과(엔트리 8개, 이미지 없을 때보다 엔트리 2개 증가) → `render`가 **"이미지 2"**로 정상 보고 → 재파싱 왕복(`--image-refs`)에서 이미지 2개가 실제 파일로 다시 추출됨(내용 손실 없는 왕복 확인).
