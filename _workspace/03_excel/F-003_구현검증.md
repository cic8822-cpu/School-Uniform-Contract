## 핵심 결함 발견: PowerShell 배열 리터럴 파싱 버그 (COM 문제 아님)

이번 세션의 대부분 시간을 소모한 결함이며, 향후 유사 작업에 매우 중요하므로 상세히 기록함.

- **증상**: `$itemsF03 = @("1번 문구", "2번 문구", "3번 문구", "4번 문구")` 형태의 4개 항목 배열을
  쓰고 `for ($i=0; $i -lt $itemsF03.Count; $i++)`로 순회했는데, 매 빌드마다 항목 2~4(B9~B11)가
  병합조차 되지 않고 빈 칸으로 남는 결함이 재현됨.
- **잘못된 초기 가설들(전부 기각)**: (1) 병합 경계를 벗어난 부분범위 서식 적용 시 Excel이 병합을
  자동 통합하는 결함(F-002에서 실제로 있었던 별개의 결함, 이번엔 아님) — 개별 행 서식 적용으로 바꿔도
  재현됨. (2) 장시간 COM 자동화 세션의 누적 부하로 인한 RPC 호출 누락 — 강제 가비지 컬렉션·순서 역전
  실행·모든 호출에 딜레이 삽입·`Cells.Item()` 인덱스 접근으로 전환 등 총 6차례 재빌드로 시도했으나
  전부 동일하게 실패함(같은 지점에서 100% 동일하게 재현되어 "비결정적"이 아님을 뒤늦게 인지함).
- **실제 원인(격리된 최소 재현으로 확정)**: 이 빌더 전체가 `[System.IO.File]::ReadAllText()` +
  `[scriptblock]::Create()` 경로로 실행되는데(UTF-8 무BOM 파일을 Windows PowerShell 5.1에서
  올바르게 읽기 위한 기존 안전 빌드 방식), 이 실행 경로에서 `@(...)` 배열 리터럴의 **첫 번째 원소가
  `"문자열A" + "문자열B"` 형태의 문자열 연결식**이면 배열 전체가 원소 1개로 붕괴하는 파서 결함이
  실제로 존재함. 6줄짜리 최소 재현 스크립트(`"1. AAAA" + "BBBB", "2. XXXX"` 2원소 배열)에서도
  100% 재현됨(`$a.Count`가 2가 아�닌 1). 문자열 연결을 제거하면(`"1. AAAABBBB"` 단일 리터럴로 병합)
  즉시 `Count=2`로 정상 동작함. 이 프로젝트의 다른 모든 배열(`$fields1`~`$fields3`, `$forms`,
  `$documentsF17`, `$flowRows` 등)은 첫 원소에 `+` 연결을 쓰지 않아 이 결함의 영향을 받지 않음을
  전수 확인함(`grep '@($'`로 전체 배열 위치를 찾아 첫 원소를 각각 대조).
- **조치**: `$itemsF03`의 첫 원소를 `"1. 20○○학년도 " + "○○학교 …"` 연결식에서 단일 리터럴 문자열
  `"1. 20○○학년도 ○○학교 …"`로 병합함. 이후 4개 항목 전부 정상적으로 병합·기록됨(자동 검증
  "F-003 4개 준수사항 항목이 원문과 일치함" PASS).
- **재발 방지**: `@(...)` 배열 리터럴을 여러 줄로 쓸 때 첫 번째 원소에는 `+` 문자열 연결을 쓰지
  않는다(필요하면 둘째 원소 이후에만 사용하거나, 처음부터 하나의 리터럴로 작성한다). 이 프로젝트의
  안전 빌드가 `[scriptblock]::Create()` 경로를 계속 쓰는 한 유효한 제약임.
